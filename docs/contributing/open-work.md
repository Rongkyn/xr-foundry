# Open-work board

The repository is the orchestrator; any person or Agent, on any device and
through any provider, is a worker. The open-work board is the dispatch surface
that tells a worker what is open, what each item waits for, and which items need
no claim at all. It is generated by `scripts/open_work.py` from files the
repository already holds. It is not a second task database and it is not
authoritative: when the board and a source file disagree, the source file wins,
and the fix is to correct the source file and regenerate.

## What the board reads

| Kind | Source | One item per |
| --- | --- | --- |
| `work_item` | `docs/contributing/work-items.json` | unfinished curated item, preserving its `needs`, `decision_class`, and unfinished dependency ids |
| `test_gap` | `docs/standards/*/coverage-map*.json` | partial clause whose missing text names a test or validator rule |
| `evidence_gap` | `docs/standards/*/coverage-map*.json` | partial clause whose missing text names a receipt, consumer run, player build, device, or Editor execution |
| `lesson_gap` | `docs/standards/lessons/lessons-register.json` | disposition with status `gap` or `deferred`, carrying its `follow_up` |
| `family_proposal` | `docs/foundry/queue/next-batch.json` | queued candidate, carrying its `exact_next_action` |
| `staging_promotion` | `staging/<family>/README.md` | staged family; it needs a Unity run and the maintainer's admission signature |
| `deliberation_open` | `docs/governance/deliberations/*.json` | record with status `open`, with `review_not_before` and whether the window has closed at run time |
| `roadmap_step` | `ROADMAP.md`, "Execution order after Inventory" | numbered item, in order |

Every item carries a stable `id` (source path plus clause, lesson, candidate, or
record id), a `family` (or `repository`), a `blocked_on` value, a `lane`, one
`next_action` sentence, and an `evidence_note` where one applies.

`work_item` entries read `blocked_on` from their explicit `needs` and `lane`
from `decision_class`. A capability requirement does not change the declared
decision class. `pending_dependencies` lists dependencies not marked `done`; an
unknown dependency stays pending and produces a warning. The full board keeps
these items visible, with their wait in `next_action`; the `--capability` view
excludes them until their prerequisites finish. Its header counts items needing
a different capability separately from otherwise reachable items waiting on
dependencies, without counting the same item twice. Invalid decision classes or
dependency lists are warned and skipped. This projects the existing
[work-item protocol](work-items.md), without granting or changing authority.

For inferred entries, `blocked_on` is read from the item's own text: `unity_editor` when it needs an
Editor run, compilation, a player build, or a consumer exercise; `headset` when
it needs a device or a Device Lab receipt; `maintainer` when it waits on an
admission, a signature, a recorded decision, or an owner-only repository
setting; `review_window` for a deliberation whose window is still open;
`nothing` otherwise. The classification is a reading of the text, not a
decision; if it is wrong, the item's source file is where the wording lives.

For those inferred entries, `lane` is `routine` only when `blocked_on` is `nothing` and the kind is a
`test_gap`, `lesson_gap`, or `roadmap_step`. Everything else is `non_routine`.

## How a worker uses it

```text
python scripts/open_work.py --markdown          # read the board
python scripts/open_work.py --json              # machine-readable, same data
python scripts/open_work.py --output board.json # write the JSON
```

1. Run the command at the repository root. The Markdown view groups items by
   lane and then by what they are blocked on; the JSON view adds a `summary`
   with counts by kind, blocker, and lane, the commit it was generated at, and a
   `warnings` list for any source file the generator could not interpret.
2. Pick an item from the **routine lane** whose capabilities you satisfy and
   whose `pending_dependencies` is empty (or use `--capability <id>`). Nothing is reserved for you and
   nothing needs to be: a routine item follows
   [`start-here.md`](start-here.md) (branch, change, one verdict command, push,
   five-line pull request). No claim, lease, anchor, or governance window.
3. A **non-routine** item says what it waits for. `unity_editor` items need
   someone with an Editor to follow
   [`../validation/run-unity-gates.md`](../validation/run-unity-gates.md);
   `headset` items need a Device Lab session under
   [`../device-lab/README.md`](../device-lab/README.md); `maintainer` items wait
   for a recorded decision; `review_window` items accept deltas until the window
   closes, as [`deliberation-protocol.md`](deliberation-protocol.md) describes.
   Coordinated or evidence-bearing work on these goes through
   [`task-hall.md`](task-hall.md).
4. When you close an item, change the source that produced it (the coverage map,
   the lessons register, the queue, the staging directory, the deliberation
   record, or the roadmap) in the same change. The next run of the board shows
   the item gone; there is no board entry to edit.

## What the board never does

- It never assigns, reserves, leases, or claims anything, for a person or an
  Agent. Two workers may pick the same routine item; the merge-readiness
  verdict and review resolve the duplicate, not the board.
- It never grants write, review, merge, release, promotion, or device authority.
- It never records progress. Progress lives in branches, pull requests, evidence
  receipts, and the source files.
- It never replaces `not_tested` with evidence. An `evidence_gap` stays open
  until the named receipt, run, or build exists and is validated.

The generator exits non-zero only when a source file cannot be read from disk. A
file with an unexpected shape is skipped and named in `warnings`, so a partial
board is always visible and never silently complete.
